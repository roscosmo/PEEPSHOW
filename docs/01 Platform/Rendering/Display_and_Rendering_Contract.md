# Display and Rendering Contract

This document defines active HW6 display ownership, Sharp Memory LCD behavior, framebuffer semantics, flush behavior, DMA-safe buffer placement, low-power display behavior, and the LPBAM display-animation path. HW5 provides the validated LPBAM baseline; HW6 must revalidate that baseline before autonomous-display capabilities are granted in an HW6 target profile.

Display is Platform-owned. Engine and Reference Game code request scene/frame presentation or animation capabilities; they must not control SPI, DMA, LPBAM, level translation, EXTCOMIN, SRAM4 placement, or panel-native row payloads directly.

## Ownership

- `thDisplay` is the sole owner of SPI3, display LPDMA, NSS behavior, framebuffer flushes, and dirty tracking.
- `thPower` coordinates RTC and low-power policy needed for `LCD_1HZ`.
- Other threads submit display requests only through `qDisplayCmd`.
- No direct display HAL/LL calls are allowed outside `thDisplay`.
- Engine/Reference Game code renders into approved abstractions and requests presentation.
- Low-level panel code lives in `LS013B7DH05.c` and is limited to Sharp Memory LCD command framing, transfer preparation, DMA/polling flush mechanics, and panel-native clear/present operations.
- The Platform display renderer lives above the panel driver in `display_renderer.c`; it owns retained logical layers, composition into the committed native framebuffer, logical-to-native drawing helpers, dirty rows, basic text/shape composition, diagnostic patterns, framebuffer hash, and minimal FW0 UI page rendering.
- The canonical compositor order is `OVERLAY`, `UI`, `SCENE`, `BACKGROUND`. FW0 currently proves one committed framebuffer and incremental cursor rows; retained per-layer storage remains pending.

## Electrical / Low-Power Rules

- The HW6 `TXU0104RUTR` path is hardwired enabled. Firmware must not create a `VLT_LCD` GPIO, translator-disable state, or duty-cycling policy.
- SPI signals and `LCD_1HZ` / EXTCOMIN therefore have a continuously enabled translator path whenever the display rail is powered.
- `LCD_1HZ` is generated by RTC calibration output and maintains EXTCOMIN/VCOM.
- The display is intended to remain visible in low power.
- HW6 Phase 0 must verify the hardwired path and confirm EXTCOMIN reaches the panel in active and STOP contexts.

## DMA-Safe Buffer Placement

HW6 display DMA/LPDMA source data must live in the SRAM4 display-DMA/autonomous arena. This allocation model is validated on HW5 and target-proven on HW6 for the first cursor-slice LPBAM handoff. The current eight-row, `250 ms` cursor slice has a measured `56 uA` five-minute average, but final renderer-driven animation budgets remain provisional until current scaling is measured across representative dirty-row, payload, chunk, and cadence limits.

| Buffer | Purpose | Placement |
|---|---|---|
| committed panel framebuffer | retained `144 x 168` 1bpp recovery/seed truth | retained non-SRAM4 runtime RAM |
| retained logical compositor layers | `OVERLAY`, `UI`, `SCENE`, `BACKGROUND` pixels plus required ownership masks | retained non-SRAM4 runtime RAM |
| display transmit scratch | Sharp LCD command/row payload stream, approximately 3,364 B including alignment | normal SRAM; GPDMA-accessible awake-transfer staging |
| compiled waiting-visual payload | `18` fixed slots of `584` bytes; each carries one `28`-row/`583`-byte autonomous transaction | fixed `10512`-byte SRAM4 payload arena |
| LPBAM/LPDMA descriptors and metadata | autonomous linked-list execution | fixed SRAM4 display-owner reservations |

The display owner exclusively sequences the SRAM4 overlay. Once an autonomous slice is armed, normal awake presentation cannot reuse the transmit scratch until the slice is stopped/unlinked or rebuilt afterward.

Packages and normal authoring tools do not name SRAM4, buffer addresses, row payload formats, dirty rows, transfer chunks, or LPBAM descriptors. They provide settled visual states and waiting-visual intent through [[Rendering_API_Contract]] and [[Asset_Pipeline_and_Package_Tooling_Contract]].

Measured allocation and admission limits are defined in [[Memory_and_Budgeting_Contract]], published through [[Target_Profile_Schema_Contract]], and evidenced in [[Brought_Up_Tracker]].

## Reactive Waiting-Visual Integration

A reactive Engine transaction may leave either a held frame or bounded waiting-visual intent. The display owner derives the backend; packages do not select LPBAM.

Required handoff:

```text
reactive transaction settles
  -> dirty logical layers composed into committed framebuffer
  -> seed frame presented through SRAM4 TX scratch
  -> waiting visual compiled against the committed seed and presentation timeline
  -> SRAM4 scratch overlaid by compiled payload
  -> autonomous slice validated and armed when admitted
  -> display owner acknowledges ready to power owner
  -> CPU enters the selected STOP-class state
```

The first autonomous transition begins from the seeded physical frame. Autonomous playback changes only presentation; it does not mutate committed package state. On wake or abort, the display owner reclaims SPI3/LPDMA/LPBAM and restores a known normal-display state before accepting new presents.

The presentation epoch, current phase, and next deadline are Engine/renderer
state, not LPBAM state. Awake rendering and autonomous playback consume the same
timeline. Backend prepare, commit, wake, and abort must not restart the
animation. On wake, the display owner and Engine reconcile elapsed time and
resume the correct phase with the remaining interval.

FW0 now has a backend selector for display waiting. `HELD_FRAME` is the default baseline STOP2 backend: a completed successful current-page render may be held through STOP2 without arming LPBAM. If an awake renderer animation is active, `thPower` must suppress that animation and request a bounded cursor-visible handoff from `thDisplay` before STOP2 entry so the held panel image is deterministic. `LPBAM` is the autonomous backend: normal display actions clear `display_lpbam_ready`, and `thPower` asks `thDisplay` for an LPBAM prepare handoff before automatic STOP2 admission may treat LPBAM as ready. `thDisplay` may satisfy STOP2 LPBAM validation only when it later reports a ready page, ready render count, and `HAL_OK` LPBAM status that still match the current UI state. The first real HW6 path now prepares and starts a debug/test cursor-slice LPBAM payload; `UNAVAILABLE` remains the correct result when no validated LPBAM slice exists for the current renderer state or target profile. If entry is abandoned after a successful prepare, `thPower` must send the display abort handoff so normal display ownership is reclaimed. FW0 target evidence validates both the older forced-ready abort shape and the real cursor-slice start/STOP2/wake/abort path.

If the preferred waiting visual does not fit the measured target budget, the display owner/compiler uses the package-declared reduced visual or hold fallback. Compilation failure must not silently convert a reactive wait into an awake polling loop.

## LPBAM Display Scenario FSM

LPBAM display animation is a hardware-validated HW5 Platform baseline for eligible reactive waiting visuals. On HW6 the owner handoff, SRAM4 placement, linked-list start, STOP2 residency, complete-cursor row-unison behavior, phase-aligned cursor handoff, wake, abort/reclaim path, and first cursor-slice current baseline are now validated. Shipping use remains target-profile gated until general waiting-animation compilation, SRAM4 admission limits, current scaling across admitted production payloads, and display electrical behavior are evidenced for production waiting visuals.

It is allowed and designed-for, but not required for the normal display renderer to function.

| State | Meaning |
|---|---|
| `LPBAM_DISP_UNAVAILABLE` | no validated LPBAM display scenario available |
| `LPBAM_DISP_PREPARE` | static frame/row sequence and resources being prepared |
| `LPBAM_DISP_VALIDATE_LIST` | linked-list scenario bounds and ownership validated |
| `LPBAM_DISP_ARMED` | scenario ready but not yet running |
| `LPBAM_DISP_RUNNING` | autonomous low-power display animation active |
| `LPBAM_DISP_WAKE_REQUESTED` | input/power/runtime event requests CPU/display owner wake |
| `LPBAM_DISP_STOPPING` | stopping LPBAM and reclaiming SPI/display resources |
| `LPBAM_DISP_FAULT` | LPBAM scenario fault |

LPBAM rules:

- LPBAM may run only Platform-validated compiled waiting-visual slices.
- LPBAM cannot own arbitrary game rendering.
- LPBAM is the preferred backend on targets that grant the autonomous-display capability for eligible display motion while reactive runtime logic waits for its next admitted event.
- Source visual states must resolve to final bounded 1bpp content before the Platform compiler packs them into the SRAM4 display-DMA/autonomous arena.
- CPU wakes when animation class changes, input arrives, storage/power event occurs, or LPBAM faults.
- Normal display owner must reclaim SPI3/LPDMA/LPBAM resources cleanly after exit.
- LPBAM does not run the renderer or package logic. It executes a compiled display program derived from the settled reactive state and its waiting-visual intent.
- Display stability and LPBAM readiness are separate states: a successful normal render may satisfy the held-frame backend, but the LPBAM backend must remain pending until `thDisplay` explicitly reports the LPBAM handoff as ready.
- `thPower` must not infer LPBAM readiness from a stable frame alone. If the selected backend is LPBAM, it must receive the display-owner prepare ACK and `HAL_OK` ready result; `UNAVAILABLE` is a valid blocked state when no validated LPBAM slice exists for the current renderer state, target profile, or visual budget.
- After a successful prepare, `thPower` must re-check hard blockers before entering STOP2. If input, UI, display, storage, queue, or other hard state changes are observed, `thPower` must send the LPBAM abort handoff and refuse sleep.

Current FW0 LPBAM cursor-slice structure:

- `thPower` selects the display wait backend. When `LPBAM` is selected, it sends a bounded prepare command to `thDisplay` before STOP2 entry and consumes the owner ACK/status instead of assuming readiness from a stable frame.
- `thDisplay` accepts the prepare only when the normal renderer has completed the current UI page successfully and the ready page/render count still match the UI router.
- Awake panel presentation and autonomous presentation use separate DMA/memory paths under the same `thDisplay` ownership. Awake row/full-frame streams are packed into a normal-SRAM staging buffer and transmitted by SPI3 through GPDMA1 channel 0. Compiled autonomous payloads, queue descriptors, and metadata remain in SRAM4 and execute through LPDMA1 channel 0. The awake staging buffer must not consume SRAM4 capacity.
- `display_renderer.c` is the sole author of cursor appearance. It copies the selected cursor's native panel region into each requested phase frame, using outlined phase `0` and solid phase `1`; both are visible. The LPBAM compiler repeats those renderer-produced phases across its four-frame bring-up sequence, compares consecutive frames within the bounded region, and packs only dirty panel rows.
- SRAM4 payload storage is a permanent target layout of `18` equal, four-byte-aligned slots. Each slot can hold one complete `28`-row, `583`-byte Sharp Memory LCD transaction; six spatial bands cover the `168` panel rows, so the target guarantees three independent full-panel states (`18 / 6`) before payload deduplication. A transition writes every row in each intersected band, even when only a smaller visual region changed. This trades some wire bytes for fixed addresses, deterministic admission, and a simple authored-animation budget.
- Payload slots are allocated deterministically and may be reused when the same spatial band has byte-identical content in another sequence step. A logical animation step references only the bands it changes. Only its first transaction waits for the LPTIM cadence edge; continuation transactions execute immediately so a multi-band logical frame remains visually coherent.
- The current renderer-owned cursor descriptor has `8` candidate rows crossing one fixed band. Each transition therefore emits one `583`-byte transaction covering panel rows `141..168`, while awake GPDMA rendering remains native-row dirty and is not expanded to the fixed LPBAM band.
- SPI3 remains at the target-proven `1 MHz` wire rate from the `4 MHz` MSIK kernel and `/4` prescaler. Its FIFO threshold is four 8-bit frames, matching each 32-bit DMA body write; reverting to a one-frame threshold recreates FIFO starvation in STOP2.
- The LPBAM scenario applies the LPTIM1 channel 1 trigger to the first transaction of each logical animation step, masks that trigger on continuation transactions, sets the queue circular, enables SPI3/LPTIM1/LPDMA1/SRAM4 autonomous clocks plus MSIK STOP support, starts LPDMA, then starts LPTIM1 at the `250 ms` frame cadence. SPI `AUTOCR.TRIGEN` remains clear because LPDMA owns cadence gating; enabling the separate SPI trigger would incorrectly pace continuation transactions as additional animation frames.
- While LPBAM is active or ready, STOP2 GPIO parking must not park the display-SPI group. On wake or abort, `thDisplay` stops LPTIM1, aborts/unlinks LPDMA, aborts SPI, restores normal SPI/LPTIM ownership, and explicitly relinks `hspi3.hdmatx` to GPDMA1 channel 0 after `HAL_SPI_Init()` reruns CubeMX MSP setup. It then clears LPBAM readiness and returns to normal display ownership. CubeMX currently initializes both SPI3 TX DMA channels and links LPDMA last, so omitting this wake-time relink routes normal-SRAM awake transfers through LPDMA and fails the first post-STOP2 render.
- The current general compiler accepts a bounded renderer-owned program containing multiple element tracks, independent phase counts, a shared sequence timeline, and panel-native candidate rows. It composes each sequence step in normal SRAM, diffs consecutive states by panel row, then packs admitted dirty rows into SRAM4 without moving visual authorship into the transport layer. Target evidence covers concurrent two-phase and four-phase elements, non-contiguous two-chunk updates, and coherent full-panel two-phase playback. Package serialization and authoring-tool budget presentation remain future layers above this contract.
- Runtime queue construction must remain in user-owned `ps_lpbam_display_queue.c`; CubeMX's `lpbam_lpbamap1_scenario_build.c` and `lpbam_lpbamap1_scenario_config.c` are non-runtime scaffolding and must remain excluded from the firmware target.
- The user-owned `ps_lpbam_dma_node_compat.c` replacements must remain authoritative for `LPBAM_SetDMATransferConfig()`, `LPBAM_SetDMATriggerConfig()`, and `LPBAM_SPI_FillNodeConfig()`. Each rebuilt node explicitly sets `Init.Mode = DMA_NORMAL`; otherwise debug builds may assert in `HAL_DMAEx_List_BuildNode()` and release builds may consume undefined mode state after regeneration.

Current phase-alignment status:

- Awake and LPBAM phase intervals are both nominally `250 ms`: ThreadX runs at `100 Hz` with a `250 ms` blink knob, while the validated LPBAM setup reports LPTIM1 `ARR/CMP=7813/7812` with `/128` at its configured kernel clock. The compare point intentionally places the first autonomous next-phase transaction at the end of the handoff interval instead of halfway through it.
- Probe API `52` preserves the idle window across cursor display-clock work, requests software compilation and queue construction ahead of the selected edge, and schedules a direct power-owner recheck after edge prearm. Payload compilation must remain in `thDisplay`; normal UI/page renders invalidate it before use.
- Evidence `EV-HW6-20260821-P1-LPBAMHANDOFF-081` closes the visible entry hitch for the current cursor unit after the general animation compiler and coherent multi-chunk transport changes: awake and LPBAM use the same renderer-authored phase identity and timeline, and the user could not perceive the STOP2 transition.
- Automatic admission is single-flight: while an LPBAM edge request is pending or in the requested state, the periodic `thPower` check may schedule its next check but must not restart or replace that handoff. This permits a zero configured quiet window without creating repeated prepare/abort churn. The selected source-to-target phase edge can still add up to approximately two `250 ms` intervals before STOP2; this is animation continuity, not input masking.
- This is a bounded two-phase validation payload, not a two-frame architectural limit. The target architecture still requires the general shared presentation timeline in [[Scene_Runtime_and_Interaction_Model]] for arbitrary authored animations and elapsed-time reconciliation. Future work must preserve the validated SPI/LPTIM clock configuration and queue packing.

LPBAM bring-up timing:

- The LPBAM experiment should be attempted after baseline full-frame update, partial update, EXTCOMIN, and static hold are proven.
- It should be attempted before final sleep/wake power integration is closed, so the power architecture can use it if it works.
- It must not block normal display bring-up or normal renderer implementation if it fails.

LPBAM acceptance criteria:

1. prevalidated frame/row sequence renders correctly
2. autonomous transfer runs without CPU intervention for the intended window
3. current draw is measured against normal RTC wake/update strategy
4. input, RTC, PMIC, storage, and fault events can wake/stop the scenario cleanly
5. `thDisplay` reclaims SPI3/LPDMA/LPBAM ownership without stale state
6. image correctness and EXTCOMIN behavior remain valid
7. failure routes to normal display owner recovery or disables LPBAM without breaking normal rendering

HW6 evidence `EV-HW6-20260820-P1-DMASRAMSPLIT-078` validates the split after repeated LPBAM STOP2 entry and wake. The build placed the `3362`-byte awake `txBuf` at `0x2000019c`, the `9216`-byte LPBAM arena at `0x28000040`, and the LPBAM queue at `0x28003140`; SRAM4 use fell from `15992` to `12632` bytes. After wake, `hspi3.hdmatx` and GPDMA1 channel 0 both resolved to `0x20016060`, while LPDMA1 channel 0 remained separate at `0x200160d8`. Awake DMA state/error were `READY/0x0`, and display completion/success/status were `1/1/0x0`. A first test without the wake-time relink reproduced the expected failure by leaving `hspi3.hdmatx` on LPDMA with display status `HAL_ERROR`; the corrected restore path passed on target.

HW6 evidence `EV-HW6-20260821-P1-LPBAMPOOL-079` validates shared resource admission for compiled waiting animations without changing the proven cursor output. The compiler now allocates from one fixed pool of `12` payload chunks instead of reserving three chunks independently for each of four sequence steps. Each sequence entry records its first chunk, chunk count, dirty native-row span, and ordering; the queue builder applies the cadence trigger only to the first chunk of each step so additional chunks complete the same visual transition. The target cursor program passed admission API/status/reason `1/0x0/0`, used sequence entries `4/4`, chunks `4/12`, and payload wire/used/capacity bytes `572/575/9216`. Its four entries remained `0/1`, `1/1`, `2/1`, and `3/1`, each covered rows `154..159`, and each payload remained `143` bytes. SRAM4 build use is `12568/16384` bytes. The remaining `3816` bytes are linker headroom for LPBAM descriptors, queue state, metadata, alignment, and future deliberate arena growth; they are not part of the published `9216`-byte authored-animation payload capacity.

## Dirty-Region Policy

Dirty update policy must define:

- dirty granularity is panel-native rows, because a Sharp Memory LCD row is the minimum update unit
- row lists are 1-based native panel rows, sorted, deduplicated, and owned by `display_renderer.c`
- threshold for full-frame fallback
- maximum low-power update budget per cycle
- orientation transform cost and ownership
- static hold behavior after a flush

Current FW0 dirty-row state:

- `display_renderer.c` owns the framebuffer-dirty source of truth and exposes a bounded dirty-row list to `thDisplay`.
- `thDisplay` presents the row list through `LCD_PresentRows_DMA()`; low-level LS013 code remains responsible only for panel packet transfer and chunking.
- Full page redraws may still mark all `168` panel rows dirty, but the renderer now keeps a committed framebuffer and computes dirty rows by diffing the newly prepared frame against the last successfully presented frame.
- HOME/list cursor movement and awake cursor blink are the current incremental test unit: both update only the cursor band and report `8/153/160` dirty rows in the validated orientation.
- Incremental page primitives must continue to erase/update only their affected rows so normal partial updates and future LPBAM payload compilation consume the same framebuffer-dirty source of truth.

Policy must be deterministic and bounded.

## Low-Power Behavior

- The display is an always-visible status surface.
- `LCD_1HZ` / EXTCOMIN must be maintained while the panel is holding an image.
- The hardwired translator remains enabled during hold, update, and STOP; software cannot duty-cycle it.
- Static installer/flashing screens should be presented once and then held with minimal activity.
- LPBAM scenarios may run only after validation and must be recoverable.

## Failure Policy

Display failure is fatal for normal operation.

On display failure:

- normal shell/game operation must not continue as if display is usable
- fault/safe path must be entered
- diagnostics should be exposed through debug/USB if available
- recovery may be attempted through the full display reinitialization path

## Validation Cases

1. first-frame bring-up correctness on LS013B7DH05
2. logical landscape `168 x 144` maps correctly to native portrait `144 x 168`
3. pixel polarity, row order, line address, and byte ordering are verified
4. partial row/region update correctness
5. full-frame fallback correctness
6. no overlapping SPI/GPDMA/LPDMA transfers, and the active SPI DMA handle matches the current awake or autonomous transport
7. `LCD_1HZ` / EXTCOMIN remains correct during static hold
8. the hardwired translator passes SPI and EXTCOMIN correctly in active and STOP contexts
9. no firmware path assumes or emits a `VLT_LCD` GPIO control
10. suspend/resume leaves no stale transfer state
11. installer/flashing static screen can hold with minimal activity
12. LPBAM idle animation experiment is attempted after baseline display validation and before sleep/wake integration closure
13. LPBAM exit cleanly returns ownership to `thDisplay`
14. display fault routes to fatal normal-operation fault path
15. renderer/panel-driver boundary remains clean: `LS013B7DH05.c` stays low-level, and diagnostic/UI composition stays in `display_renderer.c`
