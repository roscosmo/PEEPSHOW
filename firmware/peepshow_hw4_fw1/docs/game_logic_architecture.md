# Game Logic Architecture (PeepShow)

This document defines where game logic lives and how it interacts with the existing systems:

- Platform + RTOS (ThreadX) + drivers
- Maps + sprites + audio asset pipeline
- Rendering + input routing
- Low-power constraints

The goal is to keep the engine portable-ish (no HAL/ThreadX in core logic) and make game content + rules authorable at a higher level (Unity-ish) via a future editor app.

---

## Design Goals

- **Portability:** game runtime has minimal platform dependencies
- **Data-driven:** maps/sprites/audio + gameplay rules are referenced by ID
- **Deterministic:** no hidden dynamic allocation; bounded update cost
- **Editor-friendly:** future tooling can generate a gamepack that firmware loads
- **Supports both top-down and side-scroller scenes**
- **Clear contracts:** “what happens” (game/engine) vs “how it is drawn” (platform/renderer)

---

## Layering

PeepShow is split into 3 layers:

### 1) Platform Layer (STM32 + ThreadX)

Owns:
- ThreadX threads
- input sampling (buttons/joystick/imu)
- display driver + DMA
- audio driver (I2S/DMA)
- storage/flash + USB MSC updates
- SWO events + tracing
- power manager / Stop2
- optional USB CDC debug (timing-sensitive; use carefully)

Provides the engine:
- tick / delta time
- input events
- asset blobs (by Asset ID)
- execution of render/audio commands

Rule: **Platform must not contain gameplay rules.**

---

### 2) Engine Runtime (Portable C)

Owns:
- world + entities
- component update loop
- physics/collision against tilemaps
- animation progression
- command buffers for render/audio
- scene manager (scene load/unload, transition timing, scene swap)

Consumes:
- `dt_ms` (or fixed tick)
- input events
- asset reads (by ID)

Produces:
- render commands
- audio commands
- optional debug markers

Rule: **Engine must not call HAL or ThreadX directly.**

---

### 3) Game Layer (PeepShow Rules)

Owns:
- pet needs + progression
- NPC behaviors
- quests and triggers
- dialogue trees
- scene transition *requests* (what + when, not how)
- content rules and tuning policy (knobs vs gamepack)

Game logic is primarily:
- components (compiled C modules)
- data (scene configs, prefabs, triggers, dialogues)
- optional FSM/rules data generated by an editor

---

## Pet Model (Shared Between STOP/STATIC and REALTIME)

The virtual pet exists in two modes:

- **STOP/STATIC mode:** pet core loop is FSM-driven and runs at low rate
- **REALTIME mode:** the pet is a playable character (entity) inside the realtime game

Both modes **MUST share one authoritative pet state model**.

Rule: there is exactly one canonical pet model struct, and all stat changes flow through it.  
Do not duplicate pet stats across STOP mode and REALTIME mode.

Recommended split:

- `pet_state_t` (persistent, authoritative)
  - hunger/energy/mood/hygiene/health/age/etc
  - progression (xp, traits)
  - timestamps used for catch-up (see below)

- `pet_avatar_t` (runtime-only, can be reset/rebuilt)
  - position/velocity
  - animation state
  - collision runtime flags (grounded, etc)
  - current scene linkage

The realtime entity references `pet_state_t` for stats, but `pet_avatar_t` is not saved as “pet progress”.

---

## Pet Stat Updates (No Double-Counting)

Pet needs decay and other time-based stat changes must **NOT** be applied twice when switching modes.

To prevent double-counting, the pet model stores a single timebase marker, e.g.:

- `last_needs_update_time`

Both STOP/STATIC and REALTIME must use the same mechanism:

- `pet_needs_catchup(now):`
  - compute elapsed time since `last_needs_update_time`
  - apply decay/progression once
  - update `last_needs_update_time = now`

Then each mode may call catch-up at its own cadence:
- STOP/STATIC: low frequency (e.g. 1 Hz RTC tick or slower)
- REALTIME: higher frequency (e.g. once per second or per N ticks)

Because they share `last_needs_update_time`, decay is never double-applied.

---

## Pet Events (Single Mutation API)

Direct stat mutation (`pet->hunger += ...`) is discouraged.

All stat changes should flow through a small API, for consistency and tooling:

- `pet_apply_event(type, value, source)`

Examples:
- `EAT`, `SLEEP`, `PLAY`, `DAMAGE`, `HEAL`, `CLEAN`

This enables:
- consistent clamping and rules
- SWO event markers (optional)
- future editor-driven scripting (events are tool-friendly)

Content-specific parameters belong in **gamepack**.  
Global tuning (rates, thresholds) belongs in **knobs**.

## Asset IDs (Unifies Everything)

Game logic never references filenames or raw pointers. Everything is referenced by an integer Asset ID.

Examples:
- `ASSET_MAP_TOWN_01`
- `ASSET_TILESET_OVERWORLD`
- `ASSET_SPR_PLAYER`
- `ASSET_SFX_BEEP`
- `ASSET_DLG_BOB_01`

At build or pack time, a manifest maps IDs to offsets in flash.

## Scenes: Top-Down vs Platformer

A Scene is:
- a map (tile layers + collision)
- a movement mode
- camera rules
- spawn rules
- optional music
- list of entities/prefabs to spawn

SceneConfig (v0):

```c
typedef enum {
    MOVE_MODE_TOPDOWN = 0,
    MOVE_MODE_PLATFORMER = 1
} move_mode_t;

typedef enum {
    CAM_LOCKED = 0,
    CAM_FOLLOW_X = 1,
    CAM_FOLLOW_XY = 2
} camera_mode_t;

typedef struct {
    uint16_t scene_id;
    uint16_t map_asset_id;
    uint16_t tileset_asset_id;
    move_mode_t move_mode;
    camera_mode_t camera_mode;
    uint16_t music_asset_id;

    int16_t gravity_q8;
    uint16_t max_entities;
} scene_config_t;
```

Top-down mode:
- gravity ignored
- no grounded state
- movement resolves freely in X/Y

Platformer mode:
- gravity enabled
- grounded/airborne states
- jump behavior
- floor/ceiling collision

This keeps one engine with per-scene behavior.

## Scene Transitions (Wipes + 1-bit Fades)

Goal: animated transitions between scenes (wipe/fade/etc) without polluting gameplay code.

### Responsibility Split

- **Game:** requests the transition style + target scene
- **Engine:** owns transition timing/state + performs scene swap (portable)
- **Renderer:** implements pixel effect (clip wipes, 1-bit dissolve fades)

### Supported Transitions (v0)

- **Wipes**
  - horizontal: left→right, right→left
  - vertical: top→bottom, bottom→top
- **Fades (1-bit)**
  - ordered dither dissolve (Bayer-style threshold)
  - noise dissolve (hash/PRNG threshold)

Note: On a 1-bit display, fades are implemented as **DISSOLVE (threshold reveal)**, not alpha blending.

### Engine Concept API

- `Engine_RequestSceneChange(next_scene_id, transition_type, duration_ms)`

Engine tracks:
- active flag
- type
- `t_start` + `duration`
- `progress` (0..1)
- `snapshot_taken` (for fades)

### Renderer Effect Model

**A) Wipes (cheap)**
- render new scene using a clip rectangle that expands with `progress`
- uses `Render_SetClipRect(...)` / `Render_ClearClip()`
- minimal postprocessing

**B) Fades (needs one extra buffer)**
- at transition start: snapshot current composed framebuffer (`old_fb`)
- each frame:
  1) render/compose new scene into framebuffer (`new_fb`)
  2) apply dissolve mix using a threshold pattern:

`out_pixel = (pattern(x,y) < threshold(progress)) ? new_pixel : old_pixel`

Patterns:
- ordered dither: small matrix (e.g. 8×8 Bayer)
- noise: stable hash/PRNG from `(x,y,seed)`

MODE TRANSITIONS: ZOOM TO/FROM PET (REALTIME <-> STOP)

Requirement:
- The STOP/STATIC mode “pet screen” is reached by zooming into the companion sprite
  from REALTIME gameplay, so the pet fills the display.
- Returning to REALTIME zooms back out to the gameplay view.

This is treated as a TRANSITION, with one additional parameter: a focal point.

Responsibility split:

- GAME / FSM: requests mode change with a zoom transition
- ENGINE: owns zoom timing/state + scene/mode swap
- RENDERER: performs the zoom draw (scaled masked sprite blit), no game logic

Transition spec additions (concept):

- transition_type includes:
  - ZOOM_IN_TO_PET   (REALTIME -> STOP)
  - ZOOM_OUT_TO_GAME (STOP -> REALTIME)

- transition payload includes:
  - focal point (screen-space) at the moment of transition start:
    - focal_x, focal_y  (pixel coords in render space)
  - pet sprite asset + frame (or resolved sprite ref)

Engine behavior (v0):

1) On ZOOM_IN_TO_PET request:
   - capture focal point from current REALTIME pet companion entity (screen coords)
   - snapshot old framebuffer if needed (optional, for fade blend)
   - animate zoom scale from 1x -> N x (until pet sprite fills screen)
   - enter STOP/STATIC loop when zoom completes (or at a defined midpoint)

2) On ZOOM_OUT_TO_GAME request:
   - keep pet sprite as source (STOP view)
   - animate scale from N x -> 1x
   - return to REALTIME gameplay scene

Rendering model (1-bit friendly):

- Use masked scaled sprite blit:
  - src_on + src_mask generated from PNG (black/white/transparent)
  - renderBlitMasked1bppScaled(...)

- Scaling is nearest-neighbor.
- Scale can be integer-only initially (1..N) for simplicity and determinism.
- Optional polish:
  - ease curve for scale progression
  - optional dither/noise dissolve layered on top at start/end

Dirty/flush policy:
- Zoom affects most of the screen per frame.
- During zoom transitions: prefer Render_MarkDirtyAll() per tick.

Rule:
- The “zoom effect” is renderer-owned; game/FSM never hand-draws zoom frames.
--------------------------------------------------------------------------

### Dirty/Flush Policy During Transitions

Transitions modify large areas per frame.

Rule:
- while transition is active, prefer `Render_MarkDirtyAll()` per tick
- once done, return to normal dirty-row operation

Hard rule:
- game code never draws wipes/fades directly; it only requests them via engine scene manager.

## Entities + Components (Unity-ish but deterministic)

Entity is a small struct:
- transform (x,y)
- velocity (vx,vy)
- collision bounds
- tags
- component instances

No dynamic allocation at runtime. Entities come from a fixed pool.

Components are compiled modules + small per-entity state blob.

Each component implements:

- `init(entity*)`
- `update(entity*, dt_ms)`
- `on_event(entity*, event)`

Example components:
- Player controller
- Pet needs
- NPC AI
- Trigger volume
- Dialogue interaction
- Animation driver
- Physics body

Component model recommendation:
- fixed maximum components per entity (4–8)
- each component has an ID + pointer to state blob

---

## Events (Game Logic Glue)

A small event bus prevents tight coupling.

Event examples:
- `EVT_INPUT_ACTION`
- `EVT_COLLISION`
- `EVT_TRIGGER_ENTER`
- `EVT_INTERACT`
- `EVT_DIALOGUE_DONE`
- `EVT_SCENE_LOAD_REQUEST`

Platform produces input events.  
Engine produces collision/trigger events.  
Game components consume and emit new events.

---

## Rendering Contract (Engine -> Platform)

Engine does not call the display driver. It writes render commands:

- draw tile layer
- draw sprite (asset id + frame + position)
- draw text
- draw UI elements

Platform consumes commands using the Sharp_MIP pipeline.

---

## Audio Contract (Engine -> Platform)

Engine queues audio commands:

- play sfx (asset id)
- start music (asset id)
- stop music

Platform drives I2S/DMA.

---

## Editor App / Gamepack Concept (v0)

The editor app generates data, not C code.

Outputs:
- `gamepack.bin` (binary blob stored in flash / USB MSC updates)
- optional PC-only: `gamepack.manifest.json`

`gamepack.bin` contains:
- header with version + CRC
- asset table: `asset_id -> offset, length, type`
- packed payloads:
  - maps, sprites, animations, audio, dialogues, scene configs, prefabs, triggers
  - (future) FSM/rule graphs exported as data

Firmware responsibilities:
- verify version + CRC
- resolve `asset_id` lookups quickly
- load scenes by `scene_id`

---

## Prefabs (Entity Templates)

Prefab describes:
- sprite/anim set
- collision bounds
- components to attach + initial parameters

Prefab data should not require recompiling firmware.

Examples:
- NPC dialogue asset id
- trigger target scene id
- movement speed
- jump strength
- pet mood decay rates

Global tunables belong in knobs.  
Content-specific params belong in the gamepack.

---

## Triggers (Fast Unity-like Gameplay)

Triggers provide high-level behavior without scripting.

Trigger defines:
- rectangle volume
- activation rule (onEnter, onExit, onInteract)
- action (load scene, start dialogue, play SFX, give item)

This is the fastest path to real gameplay.

---

## Recommended Implementation Order (Game Logic)

1. SceneConfig + scene loader
2. Scene transition support (wipe + dither fade)
3. Entity pool + spawn system
4. Component update loop
5. Trigger component + actions:
   - load scene (with optional transition spec)
   - start dialogue
   - play sfx
6. Player controller (topdown + platformer branches)
7. NPC + dialogue component
8. Optional FSM/rule data layer for richer behaviors

---

## Rules

- Engine runtime must remain portable: **no HAL/ThreadX calls inside `engine/`**
- Game logic references assets only by ID
- Prefer data-driven triggers and prefabs over hardcoded interactions
- Add knobs only for global tunables; keep content params in gamepack
- Keep update cost bounded (fixed pools, fixed command buffers)
- Scene transitions are engine-owned; renderer owns the pixel effect; game only requests them
